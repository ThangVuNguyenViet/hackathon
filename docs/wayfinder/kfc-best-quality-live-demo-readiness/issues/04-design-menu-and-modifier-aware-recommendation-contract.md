## Question

How must the agent combine verified menu evidence, combo composition, modifier compatibility, current cart, budget, party size, prior short turns, and explicit customer preferences to suggest dishes and upsizes without keyword hard-coding or unsupported inference? Define candidate generation, ranking, ambiguity handling, one-item references such as `lấy cái đầu`, no-mutation-before-consent rules, cart-conversion equivalence, upsize pricing, stale-context suppression, and customer-facing evidence. Include adversarial cases where a requested modifier is unavailable or only some suggested dishes support it.

## Decisions captured

- When multiple verified items or configurations satisfy a request, present at most three ranked choices and do not mutate the cart. Mutation requires the customer to name one choice or use an unambiguous ordinal such as `lấy cái đầu` against that still-current presented list.
- Explicit constraints such as required spiciness, a hard maximum budget, or a required modifier are eligibility filters and never lose to a higher ranking score. Approximate language such as `khoảng 150k` may rank by closeness, but an over-budget option must be disclosed and requires explicit approval before mutation.
- Before an address resolves a store, verified generic-catalog items may be recommended and explicitly added to a draft cart with a disclosure that store availability remains unchecked. Checkout stays blocked until the configured environment provider verifies store-specific availability.
- An ordinal reference is valid only as the direct customer reply to the latest presented choice list in the same Commerce Environment and catalog snapshot, with no intervening cart or recommendation change. Otherwise the agent asks the customer to choose again.
- A cart-to-combo replacement is called equivalent only when verified component types, required quantities, and applicable modifier choices match as a multiset. A near match may be suggested only with every composition and price difference shown; any replacement requires explicit approval.
- Upsize pricing comes only from the selected item's compatible modifier-group delta, never from standalone item-price differences. The presentation shows every changed group, each delta, and the resulting cart total; without a verified delta it makes no priced upsize claim.
- Only modifier-compatible items may be presented as satisfying a requested modifier. Incompatible alternatives may appear separately only with the missing modifier stated; if none support the request, the agent says so and offers verified alternatives without representing them as matches.
- A remembered or prior-turn preference may influence candidate ranking and the explanation, but it never authorizes a modifier selection. Configuring the current item requires an explicit current-turn choice or GenUI action.
- Recommendations use deterministic eligibility filters, scored ranking among eligible candidates, and deterministic safety re-ranking. Until representative customer-behavior data exists, a transparent hand-authored score uses current-request match, party-size coverage, approximate budget fit, explicit preferences, and cart disruption; stable item code breaks ties. The current lexicographic order remains the cold-start fallback. Later learning-to-rank may replace only the scoring stage after impression, position, selection/rejection, cart, order, repeat-purchase, and feedback evidence supports offline evaluation and controlled comparison. The model never overrides eligibility or invents commerce evidence.
- An explicit add request may mutate the draft cart immediately only when it resolves to exactly one Eligible Recommendation Candidate and specifies quantity plus every required modifier. Otherwise the agent renders the missing choices and waits for completion.
- Customer-facing recommendations do not expose raw scores. They show the verified item and price, relevant composition or modifier, and one concise reason tied to the request, plus any applicable unchecked store availability or budget-overage disclosure. Score components remain proof and monitoring metadata.

## Resolution

Use one four-boundary recommendation path: deterministic candidate generation and eligibility from current Verified Commerce Facts, scored ranking among eligible candidates, deterministic safety re-ranking, then presentation of at most three choices. Hard request constraints, exact modifier compatibility, known store availability, verified prices and deltas, Commerce Environment and catalog-snapshot freshness, and mutation consent are never score trade-offs. This follows the established candidate-generation, scoring, and re-ranking architecture described by [Google's recommendation-system guidance](https://developers.google.com/machine-learning/recommendation/overview/types).

Until representative customer-behavior data exists, rank with a transparent hand-authored score over current-request match, party-size coverage, approximate-budget fit, explicit or remembered preferences, and cart disruption; use stable item code only as the final tie-breaker. If scoring is unavailable, use the deterministic lexicographic baseline over the same eligible set. If eligibility evidence is missing or stale, recommend nothing and clarify or report unavailability. Never fall back to LLM ordering, fixture order, random choice, or cross-environment evidence.

The future learned ranker's primary objective is an accepted recommendation that leads to a completed, non-refunded order. Revenue and margin are bounded secondary tie-breakers only. Visits, impressions, selections, rejections, cart changes, purchases, reviews, cancellations, and refunds remain separate signals rather than one undifferentiated label; [TensorFlow Recommenders' multi-task guidance](https://www.tensorflow.org/recommenders/examples/multitask/) supports combining rich but differently strong e-commerce signals without optimizing one proxy at the expense of overall performance. Scripted sandbox interaction remains proof evidence and is not represented as customer-preference training data.

Log an impression only when an item is actually visible, with its position, surface, request and constraint revision, eligible set, pre- and post-rerank position, score components, reason codes, Commerce Environment, catalog snapshot, feature and eligibility schema, ranker and calibration version, training-data snapshot, experiment id, and pseudonymous session/customer binding. Do not train naively on clicks or selections: position affects interaction, and [counterfactual learning-to-rank research](https://www.microsoft.com/en-us/research/publication/unbiased-learning-rank-biased-feedback/) establishes propensity weighting as a correction for biased implicit feedback. Keep fixed holdouts and a stable baseline slice, monitor training-serving skew, drift, and exposure concentration, and retrain in controlled versioned batches rather than from an automatic self-reinforcing loop.

A learned ranker may replace only the scoring stage after chronological, customer-disjoint offline evaluation beats the deterministic baseline with zero eligibility violations. Evaluate the top-three surface with nDCG@3, MRR or HitRate@3, Precision/Recall@3, outcome calibration, catalog coverage, exposure concentration, and cold-start and customer-segment slices; [Linux Foundation Recommenders](https://github.com/recommenders-team/recommenders) provides the standard ranking-metric baseline. Then use shadow evaluation followed by a pre-declared, rollback-capable online experiment. Completed non-refunded orders must improve without regression in rejection/removal, cancellation/refund/complaint, checkout completion, latency, exposure concentration, or any hard contract.

Exploration starts at zero. After those gates, an experiment may explore only open-ended recommendation turns, only among already eligible items, in at most one of the three displayed slots, with `<=5%` of eligible sessions as the initial experiment cap. Exploration never changes an exact-item request, selects a modifier, mutates a cart, relaxes a constraint, or authorizes checkout. Increasing that cap requires a separately reviewed experiment.

The LLM extracts typed hard constraints, soft preferences, party size, budget, and references, then verbalizes supplied verified reason codes. Project-owned code generates and filters candidates, a typed ranker scores them, deterministic code safety-reranks them, and StateGraph binds the presented list to environment, catalog snapshot, cart revision, and recommendation revision. An ordinal such as `lấy cái đầu` is accepted only as the direct reply to that still-current binding. The LLM cannot create eligibility, scores, explanations, item or modifier facts, or mutation authority. This separation matches [Microsoft RecAI's InteRecAgent](https://github.com/microsoft/RecAI/tree/main/InteRecAgent) pattern of using the LLM for interaction and intent parsing while domain tools perform retrieval and ranking; it does not require a separate recommender agent.

An explicit add mutates immediately only for exactly one eligible item with quantity and every required modifier specified. Otherwise the assistant presents the missing choice. Generic-catalog recommendations before address resolution disclose unchecked store availability and cannot proceed to checkout without provider verification. Combo equivalence requires a complete component-and-modifier multiset match; near matches disclose every difference and require approval. Upsizes use only verified compatible modifier deltas, showing each delta and the resulting total. Incompatible items never satisfy a requested modifier, and remembered preferences may rank or explain but never silently configure an item.

Runtime features, customer identities, interaction logs, and customer embeddings remain purpose-bound, minimized, pseudonymous, and isolated between production and sandbox. A versioned ranker artifact may be promoted through release controls, but customer data never crosses the Commerce Environment boundary. Customers see verified item facts and a concise relevant reason, never raw scores or internal provenance.
